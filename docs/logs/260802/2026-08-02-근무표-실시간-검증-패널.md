# 근무표 실시간 검증 패널(§4.8) — 백엔드·프론트 구현

- 브랜치: `feat17/roster-validation-panel`
- 근거: `docs/plan/dev_plan_0720.md` §4.8 "실시간 검증 패널(우측 고정) — 편집할 때마다 재계산:
  월별 인력산정 결과(§4.2), 일별 주/야 인원 미달일 하이라이트(§4.5), 가산 예상 점수(§4.3)"

## 배경

근무표 편집기에는 결재함 사이드바만 있고, 스펙에 명시된 실시간 검증 패널(월별 인력산정·가산
점수)은 미구현 상태였다. §4.5(일별 주/야 미달)는 이미 그리드 하단 요약행에 구현되어 있어
이번 작업 범위에서 제외했다. §4.2·§4.3 계산에 필요한 `RegulationParamSet`(고시 파라미터),
`MonthlyCensus`(월별 현원), `PublicHoliday`(공휴일) 테이블은 스키마에는 있었지만 API 레이어가
전혀 없었다(설정 CRUD 화면 A-6도 이번 범위 밖 — 후속 과제).

## 백엔드

- `RosterValidationService`(신규) — §4.1 월 기준근무시간(공휴일 대조), §4.2 직군별 필요/환산
  인원(가산 산정 반올림: 충족 인원 + 미달자 근무시간 합산 ÷ 기준시간, 소수점 버림), §4.3 가산
  3종(인력배치추가/야간직원배치/간호사배치) 계산. `RegulationParamSet` 또는 `MonthlyCensus`가
  없으면 에러 대신 `configMissing: true`로 응답해 화면에서 "설정 필요" 안내로 처리.
  - §4.2 표의 "간호(조무)사"·"물리(작업)치료사"는 `JobRole` enum 두 값을 한 행으로 합산하므로,
    `JobRole`과 별개로 11개 항목의 `StaffingCategory`를 새로 정의해 매핑.
  - §4.3② 야간/주간 실근무시간은 Phase 3(GPS) 전까지 근무표 계획 시간으로 대체(스펙이 명시적으로
    허용) — 기존 코드(`buildSummary`)와 동일하게 `shiftType.crossesMidnight`를 야간 판정
    기준으로 재사용(정확한 22~06시 구간 슬라이싱은 하지 않음).
  - §4.3③ "입소자 50인 이상 시설 +0.2점"은 원문이 "최종 가산점수에 추가"라고만 되어 있어
    RN 유무와 무관하게 항상 더하는 것으로 해석(테스트에 근거 명시).
- `RosterResponseDto.validation: RosterValidationDto` 필드 추가, `RosterService.getRoster()`에서
  `RosterValidationService.compute()` 결과를 채워 반환(기존 Promise.all에 병렬 추가).
- `roster-validation.service.spec.ts`(신규, 12건): §4.1 산식/override, §4.2 반올림·NURSE+NURSE_AIDE
  합산·입소자 임계값(50/100명)·위탁급식·세탁 면제, §4.3①②③ 각 조건의 양성/음성 케이스.
- `prisma/seed.ts`: `RegulationParamSet`(스키마 기본값 = 원문 수치 그대로, override 없음),
  `MonthlyCensus`(시드 근무표 월 2026-07, 현원 55명), `Facility.addonTargetScore`(15.0점) 추가.
  재시드 가드(`scheduleEntry` 존재 시 스킵)보다 **앞에** 배치해, 근무표 픽스처가 이미 있는
  환경에서도 검증 패널 입력값은 항상 보장되도록 함.

## 프론트

- `validation-panel.tsx`(신규): 월별 인력산정 표(직군·환산/필요 인원·충족 배지), 가산 예상 점수
  카드(진행 바 + ①②③ breakdown + "계획 기준 추정치" 라벨), 일별 미달일 요약(기존
  `roster.summary`의 `dayShortage`/`nightShortage`를 칩으로 재사용 — 미니맵을 별도로 새로 만들지
  않음, 그리드 하단 요약행과 중복 방지). `configMissing`이면 "설정 필요" 안내로 대체.
- `roster-side-panel.tsx`(신규): 우측 고정 패널의 aside 셸(폭·테두리) 소유 + `검증`/`결재함` 탭

- `labels.ts`: §4.2 11개 직군행 한글 라벨(`STAFFING_CATEGORY_LABELS`) 추가.
- 백엔드 DTO 변경 반영을 위해 `openapi:export` + `generate:api` 재실행. 사이드 이펙트로
  이전에 미반영 상태였던 attendance/clock-tag 관련 생성 타입도 함께 갱신됨(별도 백엔드 변경
  없이 기존 API 표면을 뒤늦게 동기화한 것 — 삭제된 파일 없음, `git diff --stat`으로 확인).

- API: `tsc --noEmit` 통과, 유닛 테스트 111건 전체 통과(신규 12건 포함).
- 웹: `tsc --noEmit`(`tsconfig.app.json`), `oxlint` 통과(경고는 기존 shadcn 프리미티브 파일들의
  react-refresh 경고로 이번 변경과 무관).
- 브라우저 실기동 확인(claude-in-chrome, `director@careshift.kr` 로그인):
  - 2026년 7월(시드 데이터) — 월별 인력산정(시설장 0/1 미달 … 요양보호사 12/27 미달 등 11행),
    가산 예상 점수 5.4점/목표 15점(①5.2 ②0 ③0.2), 일별 미달일 "없음"이 시드 데이터와 정합하게
    렌더링됨을 확인. `GET /api/rosters` 응답의 `validation` 필드를 curl로도 직접 대조.
  - 2026년 8월(고시 파라미터는 있으나 해당 월 `MonthlyCensus` 없음) — "검증에 필요한 설정이
    없습니다" 안내가 정상 표시됨.
  - 검증/결재함 탭 전환 정상 동작, 콘솔 에러 없음.
  - 브라우저 검증 중 발견(이번 변경과 무관한 기존 이슈): `apps/web/.env`의
    `VITE_API_URL=http://192.168.219.101:3000`(LAN IP, `4a30300` 커밋)로 인해 로그인 쿠키가
    `SameSite=Lax` cross-site 정책에 걸려 이후 인증 API 호출이 401로 실패, `/login`으로
    강제 이동하는 문제를 확인. 로컬 검증은 `apps/web/.env.local`(gitignore 대상, 커밋 안 함)로
    `VITE_API_URL=http://localhost:3000`을 임시 오버라이드해 우회했고, 검증 후 파일은 삭제함.
    이 브랜치의 변경사항과는 무관하므로 별도 이슈로 남겨둠(로컬호스트로 웹을 띄워 확인할 때
    한해 재현됨 — LAN IP로 접속하는 실사용 시나리오에서는 발생하지 않을 가능성이 높음).

## 리뷰 후속 수정 — 요양보호사 배치비율 소스 일관성

- 코드 리뷰에서 `requiredHeadcount`의 CAREGIVER 항목만 `Facility.staffingRatio`를 쓰고
  `NURSE_OR_AIDE`/`COOK`은 `RegulationParamSet.ratioNursePer`/`ratioCookPer`를 쓰는 불일치,
  그리고 `RegulationParamSet.ratioCaregiver`가 정의만 되고 어디서도 읽히지 않는 죽은 필드라는
  점이 지적됨.
- 두 필드의 성격이 달라(`ratioCaregiver`=고시 개정치 관리용 기본값, `Facility.staffingRatio`=
  `CHECK(2.1/2.3)`로 시설 유형을 나타내는 시설별 값) 어느 한쪽으로 완전히 치환하면 다른 쪽 의미가
  사라지므로, 사용자 확인 후 **기본값은 `params.ratioCaregiver`, `Facility.staffingRatio`가 그
  기본값과 다를 때만 시설별 override로 우선 적용**하는 방식으로 결정.
- `roster-validation.service.ts`의 CAREGIVER 분기 수정, 관련 유닛 테스트 2건 추가(override 적용
  케이스, override 없음 케이스 — 고시 개정치를 그대로 따르는지 확인). API 유닛 테스트 113건 전체
  통과, `tsc --noEmit` 통과.
- 한계: `Facility.staffingRatio`가 NOT NULL 기본값 필드라 "명시적 override 여부"를 나타내는
  별도 플래그가 없다. 향후 고시 기본값이 재개정되면, 아직 재분류되지 않은 시설의 구 기본값이
  새 기본값과 달라져 의도치 않게 override로 인식될 수 있다 — 근본 해결은 스키마에 nullable
  override 컬럼을 추가하는 것(DB 변경 필요, 이번 범위 밖).
