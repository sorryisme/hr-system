# 근무표 프리셋 적용 (POST /rosters/:id/apply-preset)

- **일자:** 2026-07-31
- **선행:** `docs/logs/260728/2026-07-28-근무표-반려취소-셀-원복.md`
- **대상 앱:** `apps/api`

---

## 1. 배경

`RosterService`/`RosterController`에는 셀 다건 편집(`PATCH /rosters/:id/entries`, `RosterStateService.updateEntries`)이
이미 구현돼 있었으나, §4.6/§4.8에 명시된 **프리셋 적용**(직원 행 우클릭 → 패턴 + 조 + 시작일 + 적용 기간)은
`roster.service.ts` 주석에만 남아 있고 실제 엔드포인트가 없었다. `shift_pattern_preset`/`shift_pattern_item`
테이블과 `schedule_entry.source`의 `PRESET` 값은 이미 스키마에 존재했지만(시드에서는 패턴을 수동 계산해
직접 셀을 만들 뿐, 이 테이블들을 실제로 조회하는 코드는 없었음), 이를 사용하는 서비스 로직이 없는 상태였다.

## 2. 변경 사항

**신규** `src/roster/dto/apply-preset.dto.ts`
- `ApplyPresetDto`(요청): `presetId`, `teamNo`, `employeeIds[]`, `startDate`, `endDate?`(생략 시 근무표 월 말일까지)
- `ApplyPresetResultDto`(응답): `id`, `appliedCount`, `skipped[]`(건너뛴 셀과 사유)

**신규** `RosterStateService.applyPreset()` (`src/roster/roster-state.service.ts`)
- 근무표 상태 검사: `updateEntries`와 동일하게 `CLOSED`/`CLOSING_APPROVAL`은 거부, `COMPLETED`에서
  적용 시 `DRAFT`로 복귀(단, 실제로 적용된 셀이 1건 이상일 때만 전이).
- 프리셋·조 검증: 프리셋이 이 시설 소속인지, `teamNo`가 `1..teamCount` 범위인지, 해당 조에
  `1..cycleDays` 전체 일차가 정의돼 있는지(`PRESET_INCOMPLETE`) 확인.
- 멀티테넌트 격리: 대상 직원이 모두 이 시설 소속인지 검증(`updateEntries`와 동일 패턴).
- **월경계 연속성(§4.6 A-2, "전월 패턴을 확인해 이어지도록 자동 입력"):** 앵커를 별도 테이블에
  저장하지 않고, `startDate` 직전 최대 `cycleDays`일의 기존 `PRESET` 셀을 역순으로 모아
  (`resolveStartDayIndex`) 프리셋 패턴과 대조한다. 후보 일차가 정확히 하나로 좁혀지면 그 다음
  일차부터 이어붙이고, 근거가 없거나(첫 적용) 모호하면(동일 근무유형 반복 등) `startDate`를
  1일차로 하는 새 앵커로 취급한다. 하루라도 비거나 `PRESET`이 아닌 셀이 나오면 그 시점에서
  역순 수집을 멈춰, 수동 편집·승인 반영이 낀 구간을 연속 구간으로 오인하지 않는다.
- **셀 보호:** DDL v1.3 `schedule_entry` 코멘트("승인 연차가 있는 셀은 프리셋이 덮어쓰지 않음")에 따라
  대상 기간에 이미 `APPROVAL`·`MANUAL` 소스로 채워진 셀은 덮어쓰지 않고 `skipped`로 보고만 한다.
  `PRESET` 소스이거나 비어 있는 셀만 upsert 대상.
- 대상 기간 전체를 `$transaction`으로 묶어 중간 실패 시 부분 적용을 방지(`updateEntries`/
  `RosterReflectionService`와 동일한 원자성 원칙).

**컨트롤러** `RosterController` (`src/roster/roster.controller.ts`)
- `POST /rosters/:id/apply-preset` 추가(`roster:write` 권한, 다른 편집 엔드포인트와 동일).

**정리** `RosterService`의 "후속 슬라이스에서 구현한다" 주석을 실제 구현 위치(`RosterStateService`/
`RosterReflectionService`) 안내로 갱신.

  전 구간이 같은 근무유형)에서는 안전하게 "새 앵커"로 폴백한다 — 이 경우 관리자가 `startDate`를
  명시적으로 다시 확인해야 한다.
- D-21(이미 지난 일자 변경 결재 필요)은 `updateEntries`와 마찬가지로 이번 범위 밖(선행 확정 대기).

  이번 범위 밖 — 기존 `roster-state.service.ts`의 다른 TODO와 동일한 사유.
