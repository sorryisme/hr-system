# 확정(APPROVED) 건 취소 신청 — CANCELED_AFTER_APPROVAL 구현

## 배경

`docs/dev-plan-0720-구현현황-비교.md` 작성 과정에서 `ApprovalRequestStatus.CANCELED_AFTER_APPROVAL`이 스키마·필터·프론트 라벨에는 존재하지만 실제로 이 값을 대입하는 코드 경로가 전무한 "미사용 상태값"임을 확인했다(`leave.service.ts`의 `cancelRequest()`가 `APPROVED` 상태를 즉시 409로 거부해 취소 신청 자체를 만들 수 없었고, `leave.service.spec.ts`에 이를 "이미 종결된 건"으로 못박은 테스트까지 있었다). dev_plan §3.4 전이규칙표는 `APPROVED | 취소 신청 | 신청자 | (별건 생성)`을 요구하므로, 이번 작업에서 그 경로를 구현했다.

## 백엔드(apps/api)

### `leave.service.ts`

- `cancelRequest()`의 상태 가드를 `OPEN_STATUSES(PENDING/INTERIM_APPROVED)` 전용에서 `APPROVED`도 통과하도록 확장(`CANCELLABLE_VIA_REQUEST = [INTERIM_APPROVED, APPROVED]`).
- `PENDING`은 기존과 동일하게 즉시 취소. `INTERIM_APPROVED`·`APPROVED`는 모두 기존 `createCancellationRequest()`(type=CANCEL, refRequestId=원건)를 그대로 재사용해 별도 결재 건을 생성 — 원건은 그대로 두고(`reserved`/`used` 유지) 취소 요청이 최종 승인될 때 원건이 종결된다.
- `EXCLUDED_STATUSES` 주석이 "취소 전이 로직 없음"으로 남아있던 걸 실제 동작(종결된 취소 건만 목록에서 제외)에 맞게 갱신.

### `approvals.service.ts`

- `applyCancellation()`을 원건 상태에 따라 분기하도록 변경:
  - 원건이 `INTERIM_APPROVED`였으면 → `CANCELED` 전환 + `reserved` 반환(기존 동작 그대로).
  - 원건이 `APPROVED`(확정)였으면 → `CANCELED_AFTER_APPROVAL` 전환 + **`used` 반환**. 최종 승인 시점(`settleBalance`)에 `reserved → used`로 이관되어 있으므로 확정 건의 취소는 `reserved`가 아니라 `used`를 되돌려야 한다는 점이 이번 구현의 핵심 포인트.
  - 원건이 이미 다른 경로로 종결된 경우(방어적)는 기존과 동일하게 무시.
- 근무표 원복(`REQUEST_REVERTED`)은 원건 정보(`RevertSource`)를 그대로 반환하는 기존 구조를 재사용 — `roster-reflection.service.ts`의 `revert()`가 `sourceRequestId` 일치 셀을 `preApprovalSnapshot`으로 복원하는 범용 로직이라 확정 반영(색칠, `isProvisional=false`) 셀에도 별도 수정 없이 그대로 동작함을 코드 확인.

### 범위 확인(수정 불필요 확인한 부분)

- `apps/web` 결재함(라벨 `labels.ts`, 배지 `badges.tsx`, 스테퍼 `approval-stepper.tsx`, 목록 `request-list.tsx`, 상세 `request-detail-panel.tsx`)은 애초에 `CANCELED_AFTER_APPROVAL`을 방어적으로 지원해 두고 있어 수정 없이 그대로 동작.
- `roster-reflection.service.ts`도 원건 상태를 가리지 않는 범용 원복 로직이라 수정 불필요.

## 프론트엔드(apps/mobile)

- `request-card.tsx`: 취소 버튼 노출 조건을 `status === 'PENDING'`에서 `status === 'PENDING' || status === 'APPROVED'`로 확장.
- `use-leave-request.ts`의 `CANCELLATION_REQUESTED` 안내 메시지("취소 요청을 접수했어요. 관리자 승인 후 취소돼요.")는 기존 로직이 상태와 무관하게 이미 일반화되어 있어 수정 없이 그대로 적용됨.

## 범위 밖

## 후속 리뷰 반영 (같은 날)

리뷰에서 두 가지가 지적되어 추가로 수정했다.

### [높음] 동시 취소 승인 시 `used`가 중복 차감될 수 있음

`applyCancellation()`이 원건 상태를 조회(`findUnique`)한 뒤 조건 없이 `update()`로 상태를 바꾸고 잔여를 차감하고 있었다. 동일 원건을 참조하는 취소 요청 2건이 동시에 최종 승인되면(둘 다 `createCancellationRequest`의 "조회 후 생성" 경합으로 만들어질 수 있음, 유일성 제약 없음) 둘 다 원건을 `APPROVED`로 읽고 `used`를 각각 차감할 위험이 있었다.

- **`approvals.service.ts`**: `applyCancellation()`의 `update()`를 읽은 시점의 `status`를 조건으로 하는 `updateMany({ where: { id, status: original.status }, ... })`로 교체. `count === 0`이면(다른 트랜잭션이 이미 처리) 이력 기록·잔여 차감·근무표 원복을 전부 스킵하고 `null`을 반환한다. 기존 `approveRequest()`의 자체 단계 전이가 쓰던 것과 동일한 낙관적 동시성 패턴.
- **`leave.service.ts`**: `cancelRequest()`의 `createCancellationRequest` 호출을 감싸는 트랜잭션을 `isolationLevel: Serializable`로 격상해, "취소 요청 존재 확인 → 생성"의 조회-후-생성 경합 자체를 줄였다(DB 유일성 제약 대신 트랜잭션 격리 수준으로 방어 — 호출 빈도가 낮은 엔드포인트라 비용 영향 미미).
- 테스트: `approvals.service.spec.ts`에 두 취소 요청이 동시에 원건을 확정 처리하려는 상황(두 번째 `updateMany`가 `count: 0`을 반환)을 시뮬레이션해 `leaveBalance.update`/`approvalHistory.create`(CANCEL)/`REQUEST_REVERTED` 발행이 전부 스킵되는지 검증하는 케이스 추가. 기존 취소 관련 단언도 `update` → `updateMany`(where에 status 조건 포함)로 갱신.

### [낮음] 중간 승인 건의 취소 버튼 문구가 실제 동작과 다름

`leave-request-page.tsx`가 백엔드 `INTERIM_APPROVED`를 화면 표시상 `PENDING`으로 접기 때문에, 버튼 문구를 `request.status`로 판단하면 중간 승인 건도 "신청 취소"(즉시 취소처럼 보임)로 표시되지만 실제로는 결재를 거쳐야 하는 `CANCELLATION_REQUESTED`가 반환돼 사용자가 오해할 수 있었다.

- `types.ts`의 `LeaveRequest`에 `requiresCancellationApproval: boolean` 필드 추가.
- `leave-request-page.tsx`의 `toLeaveRequest()`에서 원본 API 상태(`dto.status === 'INTERIM_APPROVED' || dto.status === 'APPROVED'`)로 이 값을 계산 — 화면 표시용으로 접힌 `status`가 아니라 원본 상태를 기준으로 판단.
- `request-card.tsx`: 버튼 라벨을 `request.status === 'APPROVED'` 대신 `request.requiresCancellationApproval`로 분기해, `INTERIM_APPROVED`·`APPROVED` 모두 "취소 신청", 순수 `PENDING`만 "신청 취소"로 표시.

`pnpm --filter api test`(116건), `pnpm --filter api build`, `pnpm --filter mobile build` 모두 재확인 통과.
