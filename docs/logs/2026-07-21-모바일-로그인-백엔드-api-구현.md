# 모바일 로그인(기기 등록) 백엔드 API 구현

- 근거 문서: `docs/plan/dev_plan_0720.md` §2.2 Phase 0(C-13), §3.8-7(기기 분실), §7 N-10
- 선행 작업: `docs/logs/2026-07-21-모바일-로그인-기능-구현.md`(프론트 Mock)
- 범위: `apps/api` — `POST /api/devices/register`와, 이를 지탱하는 기기 등록 기반 세션 처리

## 배경

`prisma/schema.prisma`의 `Employee.pinHash`, `UserDevice`, DDL 주석("기기등록 + PIN 인증,
관리자 발급 코드로 최초 1회 등록 — C-13/N-10")이 이미 이 기능의 데이터 모델을 정의하고
있었다. 관리자가 `employee.pin_hash`에 발급한 코드(6자리)를 종사자가 앱에 입력하면, 코드만으로
대상 직원을 특정해 기기를 등록하고 즉시 로그인시키는 구조로 구현했다.

관리자 측 코드 발급 화면/API, 기기 원격 로그아웃(해제) API는 이번 범위 밖 — 여전히 별도 작업으로
남는다(아래 미결 사항 참고). 이번 작업은 모바일 앱이 호출할 등록 엔드포인트와, 기기 분실 시
원격 로그아웃이 실제로 즉시 반영되도록 하는 인증 가드 쪽 선행 조건까지다.

## 구현 내용

### 신규 — `apps/api/src/devices/`

- `devices.controller.ts`: `POST /devices/register`(`@Public()`). 관리자 웹 로그인과 동일하게
  토큰은 응답 바디가 아닌 httpOnly 쿠키(`cs_access_token`)로만 전달(CLAUDE.md).
- `devices.service.ts`: 코드 검증 → 기기 등록 → 세션 발급.
  - 모바일 화면이 코드 6자리만 받고 이메일/사번을 받지 않으므로, `ACTIVE`·`pinHash` 보유
    직원을 조회해 순서대로 scrypt 비교(`verifyPassword` 재사용)로 대상을 특정한다. 시설 1곳
    규모의 대기 코드 수를 전제로 한 설계 — 대량화 시 재검토 필요.
  - 등록 성공 시 코드는 소진(`pinHash = null`) — 재등록도 관리자가 새로 발급한 코드로만
    가능하게 한다(엣지 7).
  - 같은 직원의 기존 활성 기기는 자동 해제한다("직원당 활성 기기 1대" 불변 조건).
  - 기기 식별자(`deviceUid`)가 이미 다른 직원에게 등록돼 있으면 409(`DEVICE_ALREADY_REGISTERED`).
- `devices.constants.ts`: `DEVICE_SESSION_TTL_SECONDS`(180일, 잠정치). N-10에 따라 관리자 웹
  세션(12h)보다 훨씬 길게 잡되, 기기 분실 대응은 만료 대기가 아니라 아래 가드 변경으로 즉시
  반영한다.
- `devices.module.ts`: `AuthModule`을 import해 동일 `JWT_SECRET`으로 서명.
- `devices.service.spec.ts`: 코드 매칭/오류·기기 충돌·기존 활성 기기 해제 경로 테스트.

### 인증 공통 부분 변경 — `apps/api/src/auth/`

- `jwt.util.ts`: `JwtPayload`에 선택적 `deviceId` 클레임 추가(`signJwt`/`verifyJwt` 양쪽). 기존
  관리자 로그인 토큰은 영향 없음(하위 호환 유지) — 회귀 테스트로 `jwt.util.spec.ts`에 라운드트립
  케이스 추가.
- `jwt-auth.guard.ts`: `deviceId` 클레임이 있는 토큰은 매 요청 `UserDevice.revokedAt`을 검사한다.
  관리자가 기기를 해제하면(엣지 7의 원격 로그아웃) 토큰 만료를 기다리지 않고 즉시 401 처리된다.
  아울러 `!employee.email` 요구 조건을 제거했다 — 종사자는 이메일 계정이 없을 수 있어(웹
  로그인 미대상), 이 조건이 있으면 기기 등록에 성공해도 이후 모든 인증 요청이 실패했다.
- `session-user.dto.ts`: `email`을 `string | null`로 변경(위와 동일한 이유). `apps/web`에서
  `user.email`을 직접 렌더링하는 곳이 없음을 확인 후 변경 — 영향 범위 없음.
- `auth.constants.ts`: `authCookieOptions(ttlSeconds?)`로 TTL을 주입받게 일반화(기본값은 기존
  관리자 웹 TTL 유지). devices 모듈이 더 긴 TTL로 재사용.
- `auth.module.ts`: `JWT_SECRET`을 `exports`에 추가.

### 기타

- `app.module.ts`: `DevicesModule` 등록.
- `main.ts`: CORS origin에 `http://localhost:5174`(apps/mobile dev 서버) 추가.
- `prisma/seed.ts`: 로컬 개발용으로 관리자(1~2, ADMIN)를 제외한 종사자 6명(3~8, STAFF)
  전원에게 서로 다른 등록 코드를 발급 상태로 시드(`pinHash`. 예: id 4 최정성 = `123456`).
  등록 성공 시 서버가 소진시키므로 재테스트하려면 `db:seed` 재실행 필요.
- `openapi.json` 재생성 + `apps/web` Orval 클라이언트 재생성(`RegisterDeviceDto` 추가,
  `SessionUserDto.email` nullable 반영). `apps/mobile`은 아직 Orval 미연동 상태라 프론트 교체는
  후속 작업.

## 미결 사항 (이번 구현에 영향, 후속 작업 필요)

- 관리자가 코드를 발급하는 화면/API(`employee.pinHash` 설정) — 미구현. 현재는 `prisma/seed.ts`
  개발용 시드로만 값이 채워진다.
- 기기 분실 시 관리자 화면에서의 원격 로그아웃 API(`UserDevice.revokedAt` 설정) — 미구현.
  `JwtAuthGuard`는 이미 이 값을 매 요청 검사하므로, 해제 API만 추가되면 즉시 동작한다.
- `apps/mobile`의 `device-auth-service.ts` Mock을 `POST /api/devices/register` 실호출로 교체하는
  작업(Orval 연동 포함) — 이번 범위 밖.
- `DEVICE_SESSION_TTL_SECONDS`(180일)는 운영 정책 확정 전 잠정치.
