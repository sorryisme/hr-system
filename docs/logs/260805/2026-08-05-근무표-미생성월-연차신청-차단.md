# 근무표 미생성 월 연차 신청 차단

## 배경

모바일(종사자 웹뷰)에서 연차·반차·유대 신청 시, 해당 월의 근무표(`Roster`)가 아직 생성되지 않았어도 신청이 그대로 접수되고 있었다. 근무표 생성 전에 휴가가 쌓이면 근무표 작성 단계에서 반영 누락·불일치가 생길 수 있어, 해당 월 근무표가 없으면 신청 자체를 막도록 요청받았다.

## 백엔드(apps/api)

### `leave.service.ts`

- `submitRequest()` 트랜잭션 맨 앞에 `assertRosterExists(tx, facilityId, targetDates)`를 추가. `targetDates`(연차는 여러 날짜·여러 달 가능)에서 파생한 `yearMonth` 전부에 대해 `tx.roster.findMany({ where: { facilityId, yearMonth: { in: [...] } } })`로 존재 여부를 확인하고, 하나라도 없으면 `NotFoundException({ code: 'ROSTER_NOT_FOUND' })`를 던진다. `roster.service.ts`의 `GET /rosters`가 이미 같은 코드(`ROSTER_NOT_FOUND`)·같은 예외 타입을 쓰고 있어 컨벤션을 맞췄다.
- 신규 `getCurrentMonthRosterStatus(facilityId)` 추가: 당월 `Roster` 존재 여부를 `{ yearMonth, exists }`로 반환. `GET /rosters`는 `roster:read` 권한이 필요해 종사자(STAFF)가 호출할 수 없으므로(`permissions.guard.ts`의 `ROLE_PERMISSIONS.STAFF = []`), 모바일 홈 화면이 신청 진입 전에 미리 확인할 수 있도록 `leave` 모듈에 권한 제약 없는 조회 엔드포인트를 별도로 뒀다.

### `leave.controller.ts`

- `GET /leave/roster-status` 추가(`@CurrentUser`의 `facilityId` 기준, 별도 권한 불요 — 기존 `leave` 컨트롤러 컨벤션과 동일하게 전역 `JwtAuthGuard`만 적용).

### `dto/roster-status.dto.ts` (신규)

- `RosterStatusDto { yearMonth: string; exists: boolean }`.

### 테스트(`leave.service.spec.ts`)

- `TxMock`에 `roster.findMany` 목 추가(기본값: 신청 대상월 `2026-07` 근무표 존재로 세팅해 기존 케이스 영향 없게 함).
- 신규 케이스 2건: 근무표 미생성 월 신청 시 `NotFoundException`(및 이후 로직 미호출 검증), 연차가 두 달에 걸치는데 그중 한 달만 근무표가 있으면 거부.

## 프론트엔드(apps/mobile)

- 서버 측 검증만으로는 신청 마법사(3단계)를 다 거친 뒤에야 실패가 드러나 UX가 나쁘므로, 홈 화면 진입 시점에 미리 막는다.
- `leave-request-page.tsx`: `useGetCurrentMonthRosterStatus()` 조회를 `useGetBalance`/`useGetMyRequests`와 같은 로딩·에러 처리 흐름에 합류시키고, `!rosterStatus.exists`를 `applyBlocked`로 `HomeScreen`에 전달.
- `home-screen.tsx`: `applyBlocked`가 true면 "휴가 신청하기" 버튼 대신 안내 문구("이번 달 근무표가 아직 준비되지 않아 신청할 수 없어요. 담당자에게 문의해 주세요.")를 보여준다 — `step1`(날짜 선택)로 진입할 방법이 이 버튼뿐이라 여기서만 막아도 충분.

### Orval 재생성

- `pnpm --filter api openapi:export && pnpm --filter mobile generate:api` 실행 → `apps/mobile/src/api/generated/endpoints.ts`에 `useGetCurrentMonthRosterStatus` 훅, `model/rosterStatusDto.ts` 생성물 추가.

## 테스트

- `pnpm --filter api test`: 12 suites / 121 tests 전체 통과.
- `pnpm --filter api build`(`nest build`), `pnpm --filter mobile build`(`tsc -b && vite build`) 모두 통과.
- `pnpm --filter mobile lint`(oxlint): 변경 파일 관련 신규 경고 없음(기존 `button.tsx`/`badge.tsx` fast-refresh 경고만 사전 존재).

## 범위 밖

- `apps/web` 관리자 근무표 화면은 이미 `roster:read` 권한으로 `GET /rosters` 404를 판별하는 로직(`roster-page.tsx`)이 있어 이번 작업과 무관.
- 근무표가 마감(`CLOSED`)된 이후 신청 제한 여부는 이번 요청 범위가 아니라 반영하지 않음 — `DRAFT`/`CLOSED` 어느 상태든 "생성되어 있으면" 통과.
