# 모바일 휴가 데이터 API 연동

## 배경

`apps/mobile`의 휴가 신청 화면(홈/신청 현황)이 `mock-data.ts`의 하드코딩된 값(연차 잔여, 유대 잔여, 신청 목록)으로만 동작하고 있었다. 조회(GET) 영역을 실제 API와 연결한다. 신청 제출/취소(POST)는 백엔드 반영 API가 아직 없어 범위 밖(기존과 동일하게 로컬 상태만 갱신).

## 백엔드(apps/api)

신규 모듈 `src/leave/` 추가, `app.module.ts`에 등록.

- `GET /leave/balance` — 로그인한 직원의 당해 연도 연차(`LeaveBalance`)·휴일대체(`SubstituteHolidayBalance`) 잔여를 반환. 행이 없으면 0으로 채운다.
- `GET /leave/requests` — 로그인한 직원 본인의 신청 이력(연차·반차·유대 타입만, 취소 상태 제외) 반환.
- 결재자용 `/requests`(`approvals:read`/`approvals:decide` 권한 필요)와 달리, 본인 데이터만 `@CurrentUser()`로 조회하므로 별도 권한 없이 전역 JWT 인증만으로 충분하다(`GET /auth/me`와 동일 패턴).
- `openapi:export`로 `openapi.json` 갱신.

## 프론트엔드(apps/mobile)

- `orval.config.ts`에 `leave` 태그 추가, `package.json`에 `generate:api` 스크립트 추가, `orval` 재실행으로 `useGetBalance`/`useGetMyRequests` 훅 생성.
- `leave-request-page.tsx`: 두 훅으로 조회 후 로딩/에러 화면 처리, 로그인 세션의 이름을 홈 화면에 전달(`MOCK_EMPLOYEE_NAME` 제거), 조회 결과를 `useLeaveRequest`의 초기값으로 주입.
- `use-leave-request.ts`: 목데이터 import 대신 `initial` 파라미터로 잔여·신청 목록을 받도록 변경. 제출/취소는 여전히 로컬 상태만 갱신(백엔드 반영 API 없음) — 이 때문에 두 조회 쿼리는 `staleTime: Infinity`로 백그라운드 재조회를 꺼서 로컬 낙관적 갱신이 덮어써지지 않게 했다.
- **`LeaveRequest.days`(day-of-month 정수) → `dates`(ISO `YYYY-MM-DD`) 로 표현 변경.** 목데이터는 항상 "이번 달" 범위로만 구성돼 day-of-month 정수로 충분했지만, 실제 신청 이력은 여러 달에 걸치므로 정수만으로는 다른 달의 같은 날짜와 겹치거나(차단 로직 오류) 잘못된 달로 표시되는 문제가 있었다. `domain.ts`에 `formatRequestDates`(신청 이력 표시용, 월 정보를 날짜 자체에서 추출), `toIsoDate`(제출 시 정수 day → ISO 변환) 추가, `blockedDaySet`은 표시 중인 year/month로 필터링하도록 시그니처 변경. 신규 신청 작성 단계(달력 선택 UI)는 여전히 "이번 달" 한정이라 day-of-month 정수를 그대로 사용(변경 없음).
- 백엔드 상태값(`PENDING`/`INTERIM_APPROVED`/`APPROVED`/`REJECTED`, 취소 계열은 목록에서 제외)을 모바일 3분류(`PENDING`/`APPROVED`/`REJECTED`)로 매핑 — `INTERIM_APPROVED`(1차 승인 완료, 결재 진행 중)는 `PENDING`으로 취급.
- `mock-data.ts` 삭제(대체 완료).

## 후속 과제

- `balanceYear`는 달력 연도 단순화(시드 데이터와 동일 가정) — §3.5 입사일 기준 연차연도 반영은 Phase 1 잔여 관리 본작업에서 처리.
- `CANCELED_AFTER_APPROVAL`(최종 APPROVED 이후 취소)은 미구현 — 모바일 UI도 대기중(PENDING/INTERIM_APPROVED) 건에만 취소 버튼을 노출하므로 이번 범위 밖으로 남겼다. ~~스키마의 `ApprovalRequestType.CANCEL`/`refRequestId` 자체 승인 워크플로도 이번에는 사용하지 않았다~~ → 후속 작업에서 INTERIM_APPROVED 취소에 한해 이 워크플로를 실제로 사용하도록 변경(아래 "관리자 승인이 필요한 취소" 절 참고). APPROVED 이후 취소는 여전히 미구현.

## 추가: 신청 제출/취소 API (같은 날 후속 작업)

`leave` 모듈에 실제 반영 API를 추가하고, 모바일의 로컬 전용 제출/취소 로직을 실제 API 호출로 교체했다.

### 백엔드

- `POST /leave/requests` — 연차·반차·유대 신청 생성.
  - 결재선 스냅샷(§3.5 엣지 12): 시설의 활성 `ApprovalLine`을 읽어 역할 지정(`approverRole`)이면 해당 역할의 현재 재직자를 조회해 `approverId`로 고정. **자기결재 회피(D-6)는 별도 재배정 로직 없이 그대로 스냅샷** — 신청자 본인이 결재자로 잡히더라도, 기존 `approvals.service.ts`의 승인 전이 로직이 이미 "대결자 또는 상위 단계 결재자가 하위 단계를 대신 결재할 수 있다"를 허용하고 있어 자연히 처리된다(예: 사무국장 본인 신청 + 전결 설정 → 시설장이 처리).
  - D-2 이중신청 차단: 본인의 진행 중(PENDING/INTERIM_APPROVED)·승인 완료(APPROVED) 건과 날짜가 겹치면 409(`DOUBLE_BOOKING`).
  - D-3 사후 신청: 대상일에 과거 날짜가 있으면 `isRetroactive: true` 자동 설정.
  - 더블탭 중복 제출 방지: `idempotencyKey`(클라이언트 생성 UUID)가 이미 존재하는 신청이면 새로 만들지 않고 기존 건을 그대로 반환.
  - 생성과 동시에 해당 잔여(`LeaveBalance`/`SubstituteHolidayBalance`)의 `reserved`를 가산.
- `POST /leave/requests/:id/cancel` — 본인 소유 + 아직 진행 중(PENDING/INTERIM_APPROVED)인 건만 취소 가능(낙관적 동시성 가드는 `approveRequest`/`rejectRequest`와 동일 패턴). ~~`CANCELED` 전이 + `reserved` 반환~~ → 이후 작업에서 PENDING/INTERIM_APPROVED 처리가 갈라짐(아래 절 참고). 최종 승인 이후 취소(`CANCELED_AFTER_APPROVAL`)는 미구현.
- 잔여 검증(연차 부족 등)은 하지 않는다 — 기존 `LeaveBalance` 주석("음수 허용, 승인 시 경고는 앱 레벨")과 동일한 관용도를 제출 단계에도 유지.
- 테스트 7건 추가(submitRequest/cancelRequest), `openapi:export` 재실행.

### 프론트엔드

- `use-leave-request.ts`를 재작성: 화면 전환·선택 상태만 로컬로 관리하고, 연차 잔여·신청 목록은 더 이상 로컬 상태로 복사하지 않는다(쿼리 결과를 그대로 props로 받는 구조로 전환). `submit()`/`cancelRequest()`는 생성된 `useSubmitRequest`/`useCancelRequest` mutation 훅으로 실제 API를 호출하고, 성공 시 `GET /leave/balance`·`GET /leave/requests` 쿼리를 무효화해 재조회한다.
- 이에 따라 조회 쿼리의 `staleTime: Infinity`/`refetchOnWindowFocus: false` 임시 조치(로컬 낙관적 갱신 보호용)를 제거 — 서버가 단일 진실 공급원이 되므로 더 이상 필요 없다.
- 제출 실패 시 서버 에러 메시지를 확인 화면에 노출(`submitError`), 제출/취소 진행 중에는 버튼 비활성화 + 문구 변경("신청하는 중…"/"취소하는 중…")으로 중복 탭 방지 및 진행 상태 표시.

## 추가: 1차 이상 승인된 건은 취소 시 관리자 승인 필요 (같은 날 후속 작업)

사용자 요청: "1차 승인 이후엔 취소 시 관리자 승인이 필요하도록 바꿔줘". 기존에는 PENDING이든 INTERIM_APPROVED든 취소를 누르면 즉시 `CANCELED`로 전환됐는데, 결재선 일부가 이미 이 신청을 승인한 뒤에 신청자 혼자 되돌릴 수 있다는 게 문제였다.

### 백엔드

- `POST /leave/requests/:id/cancel`의 분기:
  - **PENDING**(아무도 승인 안 함): 기존과 동일하게 즉시 취소.
  - **INTERIM_APPROVED**(1차 이상 승인 완료): 즉시 취소하지 않고, 스키마에 이미 있던 `ApprovalRequestType.CANCEL`/`refRequestId` 취소 요청을 생성해 기존 3단계 결재선(사회복지사→사무국장→시설장)을 그대로 태운다. 응답의 `result` 필드로 `CANCELED`/`CANCELLATION_REQUESTED`를 구분한다.
  - 원건(연차 등)은 취소 요청이 결정되기 전까지 손대지 않는다 — `reserved`도 그대로 잠겨 있고 상태도 INTERIM_APPROVED 그대로다.
- **원건 이중 처리 방지**: `approvals.service.ts`의 `loadForTransition`에 가드를 추가해, 어떤 건이든 자신을 대상으로 한 진행 중인 취소 요청(type=CANCEL, status open)이 있으면 승인/반려 자체를 막는다(409 `CANCELLATION_PENDING`). 이게 없으면 취소 요청이 결재 진행 중인 동안에도 원건의 남은 결재 단계가 계속 진행돼 상태가 꼬일 수 있었다.
- **취소 요청이 최종 승인되면**: `approvals.service.ts`의 `approveRequest`에서 `type === CANCEL && isFinal`일 때 `applyCancellation`을 호출해 원건을 `CANCELED`로 전환하고, `reserved`를 반환하고, 원건 쪽에도 `ApprovalHistory`(action=CANCEL)를 남긴다. 반려되면 원건은 그대로 살아있다(취소 요청 자체의 `leaveDays`가 null이라 `settleBalance`가 애초에 아무 것도 안 건드림).
- 자기결재 회피(D-6)는 취소 요청에도 별도 로직 없이 기존 대결자/상위 결재자 허용 규칙이 그대로 적용된다.
- `GET /leave/requests` 응답에 `pendingCancellation: boolean` 추가 — 이 신청을 대상으로 진행 중인 취소 요청이 있는지 여부(배치 조회로 N+1 방지).
- 테스트 11건 추가(승인 가드 4건 + 서비스 3건), `openapi:export` 재실행.
- 범위: 사용자 확인에 따라 이 정책은 INTERIM_APPROVED에만 적용하고, 이미 최종 APPROVED된 건의 취소(`CANCELED_AFTER_APPROVAL`)는 여전히 범위 밖으로 남겼다(그대로 거부).

### 프론트엔드

- `RequestCard`가 `pendingCancellation`이 true인 항목은 "신청 취소" 버튼 대신 "취소 승인 대기중" 배지(`CancellationPendingPill`)를 보여준다 — 중복으로 취소 요청을 또 누르는 걸 막는다(어차피 백엔드도 409로 막지만 UX상 처음부터 숨긴다).
- 취소 응답의 `result`에 따라 안내 문구를 다르게 띄운다: `CANCELED`는 목록에서 바로 사라지고, `CANCELLATION_REQUESTED`는 "취소 요청을 접수했어요. 관리자 승인 후 취소돼요."를 신청 현황 화면 상단에 표시(`cancelMessage`).
