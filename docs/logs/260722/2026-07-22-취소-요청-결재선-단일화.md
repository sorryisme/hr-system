# 취소 요청(CANCEL) 결재선 단일화 — 1단계 제한 + 결재자 전원 승인 허용

## 배경

사용자 요청: "결재 취소 건에 대해서 결재라인은 1개로 제한하고 결재권자 누구든지 결재가 가능하도록 해줘".

기존 `createCancellationRequest`(`leave.service.ts`)는 일반 휴가 신청과 동일한 `resolveRequestLines`를 그대로 재사용해, 취소 요청도 시설의 1~3단계 결재선(사회복지사→사무국장→시설장)을 순차로 태우고 있었다. 확인 결과 이번 변경 범위는 취소 요청(type=CANCEL)에 한정하고, 일반 연차·반차·유대 신청의 다단계 순차 결재는 그대로 유지하기로 했다. "결재권자 누구든지"는 해당 시설 결재선에 등록된 결재자(1~3단계 전원) 중 아무나를 의미한다.

## 스키마 변경

`ApprovalRequestLine`의 기존 PK `(requestId, stepNo)`는 한 단계에 결재자 1명만 허용해, "같은 단계에 여러 결재자 후보"를 표현할 수 없었다. PK를 `(requestId, stepNo, approverId)`로 변경해 같은 stepNo에 여러 후보 행을 저장할 수 있게 했다.

- `prisma/schema.prisma`: `ApprovalRequestLine` `@@id` 변경.
- 마이그레이션 `20260722000000_approval_request_line_multi_approver`: `ALTER TABLE approval_request_line DROP PRIMARY KEY, ADD PRIMARY KEY (request_id, step_no, approver_id)` — 손으로 작성(기존 마이그레이션들과 동일 관례), 로컬 DB에 적용 완료.
- `docs/ddl/carehome_tms_ddl_v1.2.sql`의 `approval_request_line` 정의도 동일하게 갱신.
- 일반 신청(1행/단계)은 영향 없음 — PK에 컬럼이 추가된 것뿐이라 기존 유일성 조건을 그대로 포함한다.

## 백엔드(apps/api)

### `leave.service.ts`

- 기존 `resolveRequestLines`(일반 신청용, 다단계 스냅샷)에서 "역할 지정 라인의 결재자 해석" 로직을 `resolveApproverId`로, "활성 결재선 조회"를 `findActiveApprovalLines`로 추출.
- `resolveCancellationRequestLines` 신설: 시설의 활성 결재선(1~3단계)을 조회해 각 단계 결재자를 해석한 뒤, **전원을 `stepNo: 1`로 고정한 후보 행**으로 반환한다(같은 사람이 여러 역할을 겸임해 중복되면 `Set`으로 제거). `deputyId`/`delegationEnabled`는 의미가 없어 항상 `null`/`false`로 저장 — 대결자·전결은 "결재선 결재자 전원이 이미 동등한 후보"인 이 구조에서는 불필요하다.
- `createCancellationRequest`가 `resolveRequestLines` 대신 `resolveCancellationRequestLines`를 사용하도록 변경.

### `approvals.service.ts`

- `resolveCurrentStep`을 "해당 stepNo의 첫 번째 행만 본다"에서 "해당 stepNo의 모든 후보 행을 검사한다"로 일반화(`find` → `filter`, `isCurrentAssignee`를 후보 배열에 대한 `some`으로 변경). 일반 신청(후보 1명)은 동작 변화 없음.
- 취소 요청은 `totalSteps = 1`이라 기존 `isFinal = nextStepNo === totalSteps` 계산이 그대로 적용돼, 후보 3명 중 누구든 승인하면 즉시 `APPROVED` 확정 → `applyCancellation`으로 원건이 `CANCELED` 전환된다(별도 분기 불필요).
- 자기결재 금지(D-6)는 기존 로직 그대로 적용 — 취소 요청자 본인이 결재선 후보 중 한 명이어도 본인 건은 결재할 수 없다.

### 테스트

- `leave.service.spec.ts`: 취소 요청 생성 테스트를 3단계 결재선(결재자 3명) 기준으로 갱신 — 3명 전원이 `stepNo: 1`의 후보로 스냅샷되는지 검증. 같은 사람이 여러 단계 결재자로 중복 지정된 경우 중복 제거되는 케이스 추가.
- `approvals.service.spec.ts`: 취소 요청은 후보 3명 중 순번과 무관하게 누구든(가장 먼저 결재한 사람) 승인 시 즉시 종결되는 케이스, 후보가 아닌 사람은 409 `NOT_YOUR_STEP`인 케이스 추가.
- 전체 40건 통과, `tsc --noEmit` / `nest build` 통과.

## 범위 밖

- 일반 휴가 신청(연차/반차/유대/근무변경)의 다단계 순차 결재·전결(D-13) 로직은 이번 변경 대상이 아니다.

## 추가: 프론트엔드 회귀 수정 (코드 리뷰 반영)

리뷰에서 지적된 대로, 위 백엔드 변경만으로는 `apps/web` 결재함 화면이 다중 결재자 후보를 다루지 못했다.

- **문제 1**: `request-detail-panel.tsx`가 `detail.requestLines.find((l) => l.stepNo === ...)`로 단계당 첫 번째 행만 취해 `currentLine`으로 사용 — 같은 stepNo에 결재자 후보가 여러 행(취소 요청) 있으면 첫 번째 후보만 `isMyTurn` 판정에 반영돼, 서버는 허용해도 두 번째·세 번째 후보의 버튼이 비활성화됐다. DB 조회에 동일 stepNo 내 정렬 기준이 없어 어떤 행이 "첫 번째"가 될지도 불안정했다.
- **문제 2**: `approval-stepper.tsx`/`signature-boxes.tsx`가 `requestLines`를 행 단위로 그대로 렌더링해, 취소 요청은 "1차" 결재 단계·서명란이 3개로 중복 표시되고 `key={line.stepNo}`도 중복돼 React reconciliation 경고가 발생했다.

**근본 수정**: 문제를 프론트엔드에서 후보를 그룹화하는 대신, API 응답 자체를 "단계 + 결재자 후보 배열" 구조로 바꿨다(리뷰가 제안한 방향).

- `request-detail.dto.ts`: `RequestLineDto.approver: EmployeeSummaryDto` → `approvers: EmployeeSummaryDto[]`.
- `approvals.service.ts`의 `toDetail`: `row.requestLines`를 stepNo로 그룹화해 단계당 한 항목(`approvers` 배열)으로 응답하도록 변경. 일반 신청(후보 1명)은 배열 길이 1로 동일하게 동작.
- `openapi:export` + `apps/web`의 `generate:api`(orval) 재실행으로 생성 클라이언트 갱신.
- `request-detail-panel.tsx`: `currentLine.approver.id === user.id` → `currentLine.approvers.some((a) => a.id === user.id)`(상위 단계 결재자 체크·전결 가능 여부 판정도 동일하게 수정). 이제 `requestLines`에 stepNo당 항목이 하나뿐이라 기존 `find()`가 안전하다.
- `approval-stepper.tsx`/`signature-boxes.tsx`: 단계당 후보 전원의 역할/이름을 나열하는 `approversLabel` 헬퍼 추가, `line.approver` 참조 제거 — 취소 요청도 "1차" 카드 1개에 후보 3명이 함께 표시된다.
- `apps/web` `tsc -b && vite build`, `oxlint`, 백엔드 `jest`(65건) 모두 통과 확인.
