# 7월 근무표 시드 — 전 교대 직원 확대 및 미결재 상태로 재개방

- **일자:** 2026-07-28
- **선행:** `2026-07-28-근무표-반려취소-셀-원복.md` (같은 날, 휴가연동 테스트용 준비)
- **대상 앱:** `apps/api`

---

## 1. 배경

반려/취소 시 근무표 셀 원복(§4.10, P1 스냅샷/복원 포함) 기능을 실사용으로 테스트하려면
근무표에 **모든 교대 직원**의 기존(수동/프리셋) 셀이 있어야 한다 — 셀이 아예 없는 직원은
가반영이 새 셀을 만들 뿐이라 "기존 근무를 덮어썼다가 반려로 복원" 시나리오를 검증할 수 없다.

기존 `seedRosterFixtures`(prisma/seed.ts)는 팀 확대(9팀 27명, `8adab3d`) 이전 6명(4~9)만
커버하고 있었다. 또한 로컬 DB를 조회해 보니 2026-07 근무표가 이미 마감 승인까지 진행돼
`CLOSED` 상태였다(수동 테스트 중 진행된 것으로 보임) — 휴가연동 테스트에는 마감 전 상태가 필요.

## 2. 변경 사항

**`prisma/seed.ts` — `seedRosterFixtures()`**
- `shiftEmployees` 배열을 4~9(기존)에서 **4~27(24명)** 로 확대.
  - 요양1·2팀(4~9): 기존 개별 패턴 그대로 유지.
  - 복지행정팀·간호재활팀 사무직·치료사(10~15, `canShiftWork` 기본값 true지만 실질 비교대 인력):
    평일 주간 고정 패턴(`OFF-D-D-D-D-D-OFF`).
  - 요양3~6팀(16~27): 요양1·2팀과 동일한 6종 순환 패턴(rotatingPatterns)을 재사용 배정.
  - 총괄 3명(1~3)은 `canShiftWork=false`라 그대로 제외(근무표 대상 아님).
- 재시드 가드(`scheduleEntry.count() > 0`)는 그대로 유지 — 완전 재시드는 여전히 로컬
  `pnpm run db:reset` 경유(CLAUDE.md, 운영 금지).

## 3. 로컬 DB 반영 (일회성 백필)

시드 스크립트의 재시드 가드 때문에 `prisma db seed`를 다시 돌려도 이미 데이터가 있어
건너뛴다. 기존 결재 픽스처(신청 13건 — 시드 10건 + 실제 테스트로 추가된 취소/반려 3건)와
다른 월 근무표(2026-08 CLOSING_APPROVAL, 2026-09 DRAFT)를 보존해야 해서 `migrate reset`
대신 최소 변경만 직접 적용했다(일회성 스크립트, 저장소에는 남기지 않음):

1. `roster`(facilityId=1, yearMonth=2026-07) `status: CLOSED → DRAFT`,
   `submittedBy/submittedAt/closedBy/closedAt=NULL`, `forceClosed=false` — **결재가 안 된
   상태로 재개방**.
2. 신규 편입 직원(10~27, 18명)에게 위 패턴 그대로 `scheduleEntry` upsert — 기존 4~9 셀·
   다른 월 근무표·결재 데이터는 손대지 않음.

## 4. 검증

- `tsc --noEmit` ✅ / `eslint`(수정한 라인 기준) ✅ — 기존 employee 배열의 줄바꿈 스타일
  경고는 이번 변경과 무관한 기존 상태라 별도로 정리하지 않음.
- 백필 후 로컬 DB 확인: 2026-07 근무표 `status=DRAFT`, 셀 보유 직원 24명(4~27) ×
  31일 = 744건, 마감 관련 필드 전부 NULL.

## 5. 참고

- 이번 로컬 DB 조정은 시드 스크립트 실행이 아니라 별도 1회성 스크립트로 적용했다 — 저장소에는
  `seed.ts` 변경분만 남아 있고, 완전히 새로운 환경(신규 클론 + `db:reset`)에서는 시드 스크립트가
  바로 24명 전체 커버리지로 시드된다.
- 다른 두 근무표(2026-08 CLOSING_APPROVAL, 2026-09 DRAFT)는 이번 작업 범위 밖이라 그대로 뒀다.
