# 결재 반려·취소 확정 시 근무표 셀 원복 (REQUEST_REVERTED)

- **일자:** 2026-07-28
- **선행:** `docs/logs/260724/2026-07-24-근무표-시드-및-결재승인-이벤트-반영.md` (다음 단계 #2)
- **대상 앱:** `apps/api`

---

## 1. 배경

`RosterReflectionService`는 `REQUEST_STEP_APPROVED`(가반영)·`REQUEST_APPROVED`(확정)를 구독해
`schedule_entry`를 반영하지만, 반대 방향(반려·취소)에 대한 구독자가 없어 다음 두 경로에서
근무표 셀이 실제 승인 상태와 어긋나는 문제가 있었다.

1. 1차 승인으로 가반영(`is_provisional=true`)된 셀이 있는데, 2차 결재자가 **반려**하면 셀이 그대로 남음.
2. 이미 승인된 연차에 대한 **취소 요청이 최종 승인**되면 원건은 `CANCELED`로 전환되고 잔여도 반환되지만,
   원건이 반영해둔 셀은 그대로 남음(`roster-reflection.service.ts`에 "원복은 후속 TODO"로 명시돼 있었음).

## 2. 변경 사항

**신설**
- `REQUEST_REVERTED`(`request.reverted`) 이벤트 + `ApprovalRevertPayload`
  (`requestId`/`facilityId`/`requesterId`/`targetDates`) — `src/events/domain-events.ts`

**공용화**
- `DomainEventBus.publish`/`subscribe`를 제네릭(`<T>`)으로 변경해, 이벤트 이름별로 다른 payload
  타입(`ApprovalReflectionPayload` | `ApprovalRevertPayload`)을 같은 버스로 주고받을 수 있게 함
  (`src/events/domain-event-bus.ts`)

**구독부** `RosterReflectionService` (`src/roster/roster-reflection.service.ts`)
- `REQUEST_REVERTED` 구독 → `revert()`: 대상 일자별로
  `scheduleEntry.deleteMany({ employeeId, workDate, sourceRequestId })` 실행.
  `sourceRequestId`가 이 요청 ID와 일치하는 셀만 지워, 그 사이 수동 편집이나 다른 결재 건이
  덮어쓴 셀은 건드리지 않는다. 애초에 반영된 셀이 없었던 경우(예: 1차 승인 전 반려)는 삭제 0건으로
  조용히 종료된다. 실패는 반영과 동일하게 로그만 남기고 전파하지 않는다.

**발행부** `ApprovalsService` (`src/approvals/approvals.service.ts`)
- `rejectRequest()`를 `approveRequest()`와 동일하게 "트랜잭션 커밋 → 커밋 이후 이벤트 발행" 구조로
  리팩터링. 반려 확정 후 해당 건 기준으로 `REQUEST_REVERTED` 발행.
- `applyCancellation()`이 `void` 대신 원건 정보(`RevertSource`)를 반환하도록 변경.
  `approveRequest()`에서 취소 요청이 최종 승인되면, 트랜잭션 커밋 이후 **원건** 기준으로
  `REQUEST_REVERTED`를 추가 발행(원건이 이미 다른 경로로 종결돼 `applyCancellation`이 `null`을
  반환하면 발행하지 않음).

## 4. 남은 한계 (1차 구현 시점)

- 취소 요청 자체가 반려되는 경우는 원래부터 원건에 영향이 없어 원복 대상이 아님(기존 테스트로 확인됨).
- 유대(SUB) 반영의 `source_ledger_id` 자동 연동은 이번 범위 밖(선행 로그의 다음 단계 #3 그대로 유효).

## 5. 코드 리뷰 반영 (같은 날 2차 수정)

1차 구현에 대한 코드 리뷰에서 P1(원복 시 승인 전 수동 근무 데이터 유실)·P2(다일자 원복 부분 적용
가능성) 2건이 지적되어 즉시 반영했다.

**P1 — 가반영이 기존 수동 셀을 덮어쓴 뒤 반려되면 원래 근무가 사라지는 문제**
- 예시: 주간근무(수동 입력) → 연차 가반영이 덮어씀 → 반려 → 기존 `deleteMany` 방식은 셀 자체를
  지워버려 원래 있던 주간근무 데이터가 영구 소실됨.
- **해결:** `schedule_entry.pre_approval_snapshot`(JSON, NULL 허용) 컬럼 신설.
  - 마이그레이션: `prisma/migrations/20260728000000_schedule_entry_pre_approval_snapshot`
    (`prisma migrate deploy`로 로컬 DB 적용 완료). DDL 문서(`docs/ddl/carehome_tms_ddl_v1.3.sql`)에
    F-04로 반영.
  - `RosterReflectionService.reflect()`: 셀을 upsert하기 전에 기존 행을 조회해, **이 요청이
    최초로 덮어쓰는 경우에만**(`existing.sourceRequestId !== payload.requestId`) 기존 상태
    (`shiftTypeId`/`source`/`isProvisional`/`overrideStart·End`/`sourceRequestId`/`sourceLedgerId`)를
    스냅샷으로 저장. 같은 요청이 두 번째로 손대는 경우(가반영→확정 전환)는 스냅샷을 다시 찍지
    않아, 가반영 상태가 "원본"으로 오인되는 것을 방지.
  - `RosterReflectionService.revert()`: 스냅샷이 있으면 그 값으로 셀을 **복원**(기존 근무로 되돌림),
    없으면(사전에 셀 자체가 없었던 경우) 기존처럼 **삭제**. 복원 후 `preApprovalSnapshot`은
    `Prisma.DbNull`로 비움.
  - BigInt/Date는 JSON에 직접 담을 수 없어 문자열로 직렬화/역직렬화(`toSnapshot`/`parseSnapshot`).
    `parseSnapshot`은 모양이 기대와 다르면 복원을 포기하고 삭제 경로로 넘어가는 방어적 파싱.

**P2 — 다일자 원복이 중간 실패 시 일부만 적용된 채 끝날 수 있는 문제**
- **해결:** `reflect()`·`revert()` 모두 대상 일자 루프 전체를 `prisma.$transaction()`으로 묶어
  원자성을 보장. 근무표 없음/근무유형 매핑 없음 등 "의도된 스킵"은 그대로 `continue`로 넘어가되,
  예기치 않은 DB 오류가 나면 해당 요청에서 이미 처리된 날짜까지 전부 롤백된다(부분 적용 방지).

**검증**
- `prisma migrate deploy` ✅ (로컬 DB, `schedule_entry.pre_approval_snapshot` 컬럼 추가 확인)
- `prisma generate` ✅
- `tsc --noEmit` / `eslint` / `nest build` 모두 ✅
- `jest` — 10 suites / 84 tests 전체 통과. `roster-reflection.service.spec.ts`에 P1(스냅샷

**남은 한계**
- 스냅샷은 1단계만 보관한다(연쇄적으로 여러 결재 건이 같은 셀을 겹쳐 덮어쓰는 경우는 범위 밖 —
  현재 비즈니스 규칙상 원건에 대한 취소 요청이 진행 중이면 원건 승인/반려 자체가 막혀 있어
  발생 가능성은 낮음).
- 유대(SUB) 반영의 `source_ledger_id` 자동 연동은 이번 범위 밖(선행 로그의 다음 단계 #3 그대로 유효).
