## 1. 구현 범위

목업 "근무표 승인" 화면을 실제 백엔드(`/api/rosters`)와 연동해 구현했다. 메인 = 근무표 그리드,
우측 = 결재함. 승인 시 결재 이벤트로 근무표 셀이 갱신되므로 처리 후 두 쿼리를 함께 무효화한다.

| 파일 | 역할 |
| --- | --- |
| `routes/roster.tsx` | `/roster` 라우트(requireAuth) |
| `features/roster/roster-page.tsx` | 월 이동 + 상태 툴바 + 그리드 + 사이드바 조합, 미존재 월 생성 |
| `features/roster/schedule-grid.tsx` | 엑셀형 그리드(직원×날짜), 팀 구분행, 하단 요약/과부족행, 셀 강조 |
| `features/roster/roster-toolbar.tsx` | 상태 배지 + 상태머신 전이(작성완료/마감상신/마감승인·반려) |

## 2. API 연동(Orval)

- `apps/api`에 roster 컨트롤러가 이미 있어 `pnpm --filter api openapi:export` → `pnpm --filter web generate:api`로
  클라이언트를 재생성했다. 생성물(`src/api/generated`)은 수정 금지 규칙 유지.
- 사용 훅: `useGetRoster`, `useCreateRoster`, `useComplete`, `useSubmitClose`, `useClose`,
  `useRejectClose`(근무표) + 기존 `useListRequests`/`useApproveRequest`/`useRejectRequest`(결재).
- 근무표 미존재 시 서버가 404 `ROSTER_NOT_FOUND` → 화면은 "근무표 생성" 유도(`retry:false`).

## 3. 셀 표기 규칙(§4.7 / §4.8)

- 표시 문자(`cellLabel`)는 백엔드가 계산해 내려주므로 프론트는 `shiftCode`→색 카테고리만 결정.
- **근무조정**(`isTimeOverridden`): 근무종류 + 조정 시각(출근/퇴근)을 세로로 쌓아 표기.
- **유급휴일대체**(`SUB`): `carryableMinutes`(150)를 `유(2,30)` 형식으로 변환.
- **가반영**(`isProvisional`): 1차 승인만 된 셀은 점선·반투명 처리(§4.10 step_approved).
- 하단 요약: `workingCount`(근무 인원), 요양보호사 주/야 인원 + `dayShortage`/`nightShortage`
  미달 셀을 빨강 `!` 표기(§4.5).

## 5. 검증 (로컬, director 로그인)

- `tsc -b` ✅ / `oxlint` ✅(경고는 기존 ui 컴포넌트 한정) / `vite build` ✅(roster 청크 분리).
- 브라우저(Playwright) E2E: 로그인 → `/roster` 렌더 확인. 콘솔 에러 0.
  - 그리드: 팀 구분행(미배정/1층팀/2층팀), 직원·직무, 색상 셀, 하단 요약(주간 미달 `1!` 빨강) 정상.
  - 결재함: 대기 4건(사후 신청 배지·단계 진행·사유), 승인/반려 버튼.
  - 카드 선택 → 해당 직원 행/대상 셀 강조.
  - 표기 안내 모달: 근무종류·내용·표기형식 표.
  - 상태 배지 "마감 완료"(로컬 roster id=1이 CLOSED 상태) + 읽기전용 안내.
- 상태머신 전이(작성완료/마감상신/마감승인·반려)는 로컬 근무표가 CLOSED라 화면 실동작 미검증 —
  전이 로직·강행 사유(D-19)·반려 사유 다이얼로그는 타입/빌드로 검증, 백엔드는 선행 슬라이스에서 HTTP 검증 완료.

## 6. 코드리뷰 반영 (2차)

리뷰 지적 4건 중 3건 수정, 1건은 근거와 함께 보류.

- **[높음] #1 승인 직후 근무표 미갱신 레이스** — 수정(완화). 백엔드 반영은 결재 응답과 비동기
  (`domain-event-bus`의 fire-and-forget)라 응답 직후 재조회가 반영 쓰기를 앞지를 수 있다.
  `roster-approval-sidebar`의 무효화 후 `REFLECTION_SETTLE_MS`(600ms) 지연 재조회를 1회 더 걸어
  뒤늦은 반영도 확실히 픽업한다. **권위 있는 정합성**(즉시 일관성/재예약)은 백엔드 아웃박스·reconcile
  후속 과제(상태머신 로그 #3)로 분리 — 프론트는 완화만.
- **[보통] #2 반려 입력 중 Space/Enter가 카드 선택 토글** — 수정. 카드 `onKeyDown`을
  `e.target === e.currentTarget`일 때만 처리(내부 Textarea·버튼에서 올라온 키 이벤트 무시).
  → 검증: 반려 사유에 공백 포함 입력 정상, 카드 선택 미토글(selected=0).
- **[보통] #3 월 무관 결재를 "위 근무표에 반영"으로 표시** — 수정. 사이드바가 `yearMonth`를 받아
  `targetDates`가 현재 월인 대기 결재만 노출. 안내 문구도 "이 달 대상"으로 수정.
  → 검증: 7월 4건 / 8월 0건("이 달 대상 대기 결재가 없습니다").
- **[보통] #4 권한 없는 사용자에 근무표 메뉴·액션 노출** — **보류(타당하나 앱 전역 이슈)**.
  근거: (1) 현재 web은 **관리자 전용**(로그인 화면 "관리자 로그인")으로 `/dashboard`·`/approvals`
  포함 **모든 라우트가 requireAuth만** 사용 — 로스터만 역할 게이팅하면 오히려 비일관, (2) `roster:*`는
  이미 web이 쓰는 결재 권한과 **동일한 ADMIN 티어**라 로스터가 특별히 더 노출되는 것은 아님,
  (3) 올바른 해법은 로그인/공용 가드 레벨의 **앱 전역 역할 게이팅**이라 auth 아키텍처 변경(별도 범위).
  서버 검증은 그대로 권위. `roster:write`/`roster:close` 액션 차등(§1.3)은 기존 문서화된 보류 항목.

> 테스트 부재(리뷰 지적)도 유효하나 `apps/web`에 테스트 러너 미설정(신규 의존성 = 사람 승인, CLAUDE.md).
> 월 변경·404 후 생성·승인 후 갱신·키보드 반려 입력 테스트는 러너 도입 후속으로 분리. 이번 반영분은
> 실 브라우저(Playwright)로 #2·#3 시나리오 검증.
