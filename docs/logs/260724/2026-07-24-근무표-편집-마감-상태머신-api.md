## 1. 구현 범위 (§4.8 상태머신)

```
DRAFT ─작성완료→ COMPLETED ─마감상신→ CLOSING_APPROVAL ─승인→ CLOSED
        └─셀수정(DRAFT 복귀)          └─반려→ DRAFT
```

`RosterStateService` 신설 + 컨트롤러에 5개 엔드포인트 추가.

| 메서드 | 경로 | 권한 | 전이/동작 |
| --- | --- | --- | --- |
| `PATCH` | `/rosters/:id/entries` | `roster:write` | 셀 다건 편집(upsert). COMPLETED→DRAFT 복귀. CLOSED 거부 |
| `POST` | `/rosters/:id/complete` | `roster:write` | DRAFT→COMPLETED + 검증 스냅샷(COMPLETED) |
| `POST` | `/rosters/:id/submit-close` | `roster:write` | COMPLETED→CLOSING_APPROVAL(submittedBy/At) |
| `POST` | `/rosters/:id/close` | `roster:close` | CLOSING_APPROVAL→CLOSED. 위반 시 강행 사유 필수(D-19) + 스냅샷(CLOSE) |
| `POST` | `/rosters/:id/reject-close` | `roster:close` | CLOSING_APPROVAL→DRAFT(사유 필수) |

**DTO:** `update-entries.dto.ts`(중첩 검증), `roster-transition.dto.ts`(Close/RejectClose 입력, `ValidationFindingDto`, `RosterTransitionResultDto`).

## 2. 주요 규칙

- **셀 편집:** 근무유형은 `shiftCode`로 지정, `override*` 시각은 쌍(둘 다/둘 다 생략) 검증. 수동 편집은 `source=MANUAL`로 두고 결재·대장 연동(`sourceRequestId`/`sourceLedgerId`)을 해제.
- **검증(§4.5):** `daily_staffing_rule`(teamId=null) 대비 요양보호사 주/야 미달을 `ValidationResult`로 스냅샷. **현재는 미달을 `BLOCK`으로 산정하는 잠정 규칙셋** — 고시 인력산정(§4.2)·가산(§4.3) 규칙은 후속 확장(코드 주석 명시).
- **마감(D-19):** BLOCK 위반 존재 + `force=false` → `409 ROSTER_HAS_VIOLATIONS`(위반 목록 반환). `force=true` + 사유 → `forceClosed=true` + `forceCloseReason` 저장 + CLOSE 스냅샷.
- **불변 규칙:** CLOSED 셀 직접 수정 → `409 ROSTER_CLOSED`(결재 경유만).
- **멀티테넌트:** 모든 전이는 세션 시설 소유 근무표만 처리(타 시설은 404 은닉).

## 5. 코드리뷰 반영 (병합 전 수정)

리뷰 지적 4건 중 3건 수정, 1건은 근거와 함께 보류.

- **[심각] #1 타 시설 직원 셀 덮어쓰기** — 수정. `updateEntries`에 (a) 입력 직원 전원이 `roster.facilityId` 소속인지 일괄 검증(`EMPLOYEE_NOT_IN_FACILITY`), (b) `upsert.update`에도 `rosterId` 명시해 셀을 항상 현재 근무표로 귀속. → 검증: 미소속 직원 `400`.
- **[높음] #2 CLOSING_APPROVAL 편집 가능** — 수정. 편집을 DRAFT/COMPLETED에서만 허용, CLOSING_APPROVAL은 `409 ROSTER_UNDER_APPROVAL`. → 검증 통과.
- **[보통] #4 날짜·월범위·ID 검증 부재** — 수정. 서비스 진입부에서 실제 달력 날짜(`INVALID_DATE`)·근무표 월 일치(`DATE_OUT_OF_MONTH`)·ID 형식(`INVALID_ID`) 선검증(트랜잭션 밖). → 3케이스 모두 `400`.
- **[높음] #3 결재↔반영 최종 일관성(아웃박스/재시도 부재)** — **보류(타당하나 범위 밖)**. 근거: (1) 계획 §2.3이 결재-근무표를 **의도적으로 느슨히 결합**(Phase 1 결재는 근무표 비의존, 과도기 수기 반영 전제), (2) transactional outbox는 **신규 테이블(마이그레이션)+소비자 재시도** 도입이라 별도 설계·리뷰 대상, (3) 현재도 반영은 **멱등(upsert)** 이고 `schedule_entry.source=APPROVAL`+`sourceRequestId`로 사후 정합 조회가 가능. → 후속으로 "APPROVED인데 미반영 건" 재조정(reconcile) 배치 또는 outbox 도입을 별도 티켓화.

> 테스트 파일 부재(리뷰 지적)도 유효. 상태 전이·격리·월경계·동시성·반영 재시도 테스트는 후속 작업으로 분리(이번 슬라이스는 실 API 호출로 시나리오 검증).
