## 1. 결론

**대부분 개발 가능**하다. 목업은 Phase 1(결재함)과 Phase 2(근무표 그리드)를 한 화면에 합쳐 놓은 형태이며,
결재 도메인은 DDL·백엔드가 이미 완비돼 있고 근무표 그리드도 골격은 스키마로 표현된다.

단, **셀 단위 근무시간 조정(override) 저장 위치가 없어** DDL 보완이 필요했다 → `v1.3`에서 반영.
근무표 모듈(roster) API는 미구현 상태로, 본 문서 §4에 스펙을 정의했다.

> 참고: `CLAUDE.md`에는 백엔드가 "스캐폴드만 존재"로 기재돼 있으나 실제로는
> `auth / approvals / leave / devices / prisma` 모듈이 이미 구현돼 있다(문서 갱신 필요).

## 3. DDL v1.3 변경 (`carehome_tms_ddl_v1.3.sql`)

v1.2를 복사해 아래 3건만 반영했다. 운영 반영은 **Migration 필수**(운영 `db push`/`migrate reset` 금지 — CLAUDE.md).

### F-01. 셀 단위 근무시간 조정 저장 위치 신설
계획 §4.8 *"모든 근무는 시간을 수정할 수 있다 → 근무종류(근무시작~종료)"* 및 목업의 근무조정 표기 근거.

- `schedule_entry.override_start_time TIME NULL` / `override_end_time TIME NULL`
  - `NULL`이면 `shift_type` 기본 시각 사용, 값이 있으면 편집기·출력에 `"근무종류(시작~종료)"` 표기.
  - 둘 다 NULL 또는 둘 다 값(앱 레벨 검증).
- `approval_request.desired_start_time TIME NULL` / `desired_end_time TIME NULL`
  - `SHIFT_CHANGE`(근무조정) 신청이 담는 희망 시각. 승인 시 셀 `override_*`로 반영.
  - 기존에는 `desired_shift_id`(유형)만 있어 "몇 시~몇 시" 정보를 담을 수 없었음.

### F-02. 유대 셀 표기 원천 연결
- `schedule_entry.source_ledger_id BIGINT UNSIGNED NULL` + `fk_entry_ledger` → `substitute_holiday_ledger(id)`
- `유(이월인정시간,분)` 표기(§4.4, 편집기 전용)를 (employee+date) 우회 조인 없이 직접 참조.

### F-03. 일별 적정 인원 시드 예시
- 목업의 하드코딩 임계값(`<=13 crit`)을 `daily_staffing_rule`로 이관하는 예시 시드(시설 전체 DAY/NIGHT min 14) 추가.

> `substitute_holiday_ledger`는 Phase 1 섹션에서 `schedule_entry`(Phase 2) **이전에** 정의되므로 FK 순서 문제 없음.

## 4. NestJS API 스펙 — 근무표(roster) 모듈 (신규)

기존 컨벤션 준수: 전역 `JwtAuthGuard` + `@RequirePermissions`, `@CurrentUser`로 행위자 식별,
DTO는 `class-validator` + `@nestjs/swagger`. 모든 업무 로직·DB 접근은 `apps/api`에만.

### 4.1 권한 문자열(신규 제안)
`permissions.guard.ts`의 `ROLE_PERMISSIONS`에 추가:

| 권한 | 의미 | 부여 대상(제안) |
| --- | --- | --- |
| `roster:read` | 근무표 조회 | SUPER_ADMIN, ADMIN |
| `roster:write` | 셀 편집·프리셋·작성완료 상신 | SUPER_ADMIN, ADMIN |
| `roster:close` | 마감 승인/강행/반려 | SUPER_ADMIN, ADMIN |

> **결정 대기:** 계획 §1.3은 *작성=사회복지사 / 마감 승인=사무국장·시설장*으로 구분하나,
> 현재 `system_role`은 사무국장·사회복지사를 모두 `ADMIN`으로 매핑한다.
> `roster:write`와 `roster:close`의 실제 차등은 **`job_role` 기반 앱 레벨 검사** 또는 RBAC 테이블 도입 시 해소.

### 4.2 엔드포인트

컨트롤러 `@Controller('rosters')`, `@ApiTags('rosters')`.

| 메서드 | 경로 | 권한 | 설명 |
| --- | --- | --- | --- |
| `GET` | `/rosters?facilityId&yearMonth` | `roster:read` | 월 근무표 헤더 + 팀별 직원 + 셀 + 하단 집계 일괄 조회(목업 렌더 1콜) |
| `POST` | `/rosters` | `roster:write` | 월 근무표 생성(DRAFT). `(facilityId, yearMonth)` 유일 |
| `PATCH` | `/rosters/:id/entries` | `roster:write` | 셀 다건 편집(드래그 일괄). COMPLETED→DRAFT 자동 복귀 |
| `POST` | `/rosters/:id/apply-preset` | `roster:write` | 프리셋 적용(패턴+시작일+기간, §4.6 월경계 연속성) |
| `GET` | `/rosters/:id/validation` | `roster:read` | 실시간 검증 결과(인력산정·과부족·가산, §4.8) |
| `POST` | `/rosters/:id/complete` | `roster:write` | DRAFT→COMPLETED. 검증 스냅샷 저장 |
| `POST` | `/rosters/:id/submit-close` | `roster:write` | COMPLETED→CLOSING_APPROVAL. 마감 결재자 알림 |
| `POST` | `/rosters/:id/close` | `roster:close` | CLOSING_APPROVAL→CLOSED. 위반 시 `force`+`reason` 필수(D-19) |
| `POST` | `/rosters/:id/reject-close` | `roster:close` | CLOSING_APPROVAL→DRAFT. 반려 사유 필수 |

### 4.3 핵심 응답 DTO 골격 (`GET /rosters`)

```ts
class RosterCellDto {
  employeeId: string;
  workDate: string;          // YYYY-MM-DD
  shiftCode: string;         // D/N/NF/OFF/AL/HAM/HPM/SUB/SICK/ABS
  cellLabel: string;         // 주/야/휴/연/오전/오후/유/조/병/결
  startTime: string | null;  // override_start_time ?? shift_type.start_time
  endTime: string | null;
  isProvisional: boolean;    // 가반영(글자만)
  source: 'MANUAL' | 'PRESET' | 'APPROVAL';
  carryableMinutes: number | null; // source_ledger_id 연동 시 "유(h,m)" 표기용
}

class RosterDaySummaryDto {
  workDate: string;
  workingCount: number;      // counts_as_work 집계
  caregiverDay: number;      // 요양보호사 주간
  caregiverNight: number;    // 요양보호사 야간
  dayShortage: boolean;      // daily_staffing_rule 대비 미달
  nightShortage: boolean;
}

class RosterResponseDto {
  id: string;
  yearMonth: string;
  status: 'DRAFT' | 'COMPLETED' | 'CLOSING_APPROVAL' | 'CLOSED';
  teams: { teamId: string; name: string; employees: EmployeeRowDto[] }[];
  cells: RosterCellDto[];
  summary: RosterDaySummaryDto[];
}
```

### 4.4 결재 → 근무표 반영(이벤트 구독)
목업의 "승인 즉시 셀 반영"은 **모듈 내부 이벤트**로 구현(계획 §2.3/§4.10):

- `request.step_approved`(1차 승인) 구독 → `schedule_entry` upsert(`is_provisional=1`, 글자만)
- `request.approved`(최종) 구독 → `is_provisional=0` 확정(색칠) + `source=APPROVAL` + `source_request_id` 기록 + 잔여 차감 표시
- `SHIFT_CHANGE` 승인 시 `desired_start/end_time` → 셀 `override_start/end_time` 반영
- 승인 연차가 있는 셀은 프리셋이 덮어쓰지 않음(앱 레벨)

> 결재 발행부는 이미 구현된 `approvals` 모듈에 존재(가정). 근무표 모듈은 **구독자만** 추가하므로 결재 코드 수정 불필요.

### 4.5 기존 결재 API(구현됨 — 재사용)
`@Controller('requests')`:
- `GET /requests?status=` (`approvals:read`) — 결재함 목록
- `GET /requests/:id` (`approvals:read`) — 상세
- `POST /requests/:id/approve` (`approvals:decide`)
- `POST /requests/:id/reject` (`approvals:decide`)

목업 사이드바(대기/처리완료·승인·반려·사유 모달)는 위 API로 이미 충족.
`same-day 연차 배지`·`사후 신청 배지`는 상세/목록 응답에 필드 추가로 대응.
