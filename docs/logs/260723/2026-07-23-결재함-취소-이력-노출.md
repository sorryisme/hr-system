# 결재함 취소 건 노출 + 진행 이력 타임라인

## 배경

결재함(A-3)이 대기/승인/반려 3개 탭으로만 기획·구현돼 있어(`plan_0720.md` 최초 기획 단계부터),
취소 확정(`CANCELED`/`CANCELED_AFTER_APPROVAL`)된 신청 건은 결재함의 어떤 탭에서도 조회할 수
없었다. 데이터(`ApprovalRequestStatus`, `approval_history` append-only 이력)는 이미 갖춰져
있었지만, 조회 진입점이 없어 취소된 건이 이후에 어떻게 처리됐는지 확인할 방법이 없었다.

## 변경 사항

### apps/api/src/approvals
- `dto/inbox-query.dto.ts`: `InboxStatusFilter`에 `CANCELED` 추가.
- `dto/request-list.dto.ts`: `InboxCountsDto`에 `canceled` 필드 추가.
- `approvals.service.ts`: `listRequests`의 `where` 분기와 탭 카운트 집계에 `CANCELED`/
  `CANCELED_AFTER_APPROVAL` 처리 추가(`CANCELED_STATUSES` 상수).
- `approvals.service.spec.ts`: `listRequests`에 대한 필터·카운트 단위 테스트 추가(기존에는
  이 메서드에 대한 테스트가 없었음).

### apps/web
- `orval.config.ts` 입력(`openapi.json`) 갱신 후 `generate:api`로 `InboxStatusFilter.CANCELED`,
  `InboxCountsDto.canceled` 재생성.
- `features/approvals/approval-inbox-page.tsx`: '취소' 탭 추가, 카운트 배지 연결.
- `features/approvals/labels.ts`: `ACTION_LABELS` 추가(이력 타임라인용), `stageSummary`에
  취소 상태 분기 추가(기존엔 취소 건이 "n/총 단계 완료"로 잘못 표시됐음).
- `features/approvals/approval-history-timeline.tsx` (신규): 서버 `histories` 배열을
  제출→승인→반려/취소 순서의 타임라인으로 렌더링. 기존에 반려 사유만 별도 박스로 보여주던
  부분을 대체.
- `features/approvals/request-detail-panel.tsx`: 반려 사유 전용 박스를 제거하고
  `ApprovalHistoryTimeline`으로 교체(반려 사유는 타임라인의 코멘트로 포함됨).
- `features/approvals/approval-stepper.tsx`: 취소 확정 건에서 남은 결재 단계가 "결재 대기"로
  보이던 버그 수정 — 브라우저로 직접 확인하는 과정에서 발견. `CANCELED`/`CANCELED_AFTER_APPROVAL`
  상태일 때 남은 단계를 "취소로 종결"로 표시하는 `canceled` 스텝 상태 추가.

## 검증

- `pnpm --filter api test`: 67개 전체 통과(신규 listRequests 테스트 2건 포함).
- `pnpm --filter web exec tsc --noEmit`, `pnpm --filter web lint`: 에러 없음.
- 로컬 MySQL + API/웹 dev 서버를 직접 띄워 브라우저로 확인. 결재함 로그인 시
  `director@careshift.kr`(ADMIN) 계정이 아닌 STAFF 계정 세션이 남아있으면 `/api/requests`가
  403(PERMISSION_DENIED)을 반환하는 것도 함께 확인 — 코드 결함은 아니고 테스트 중 발견한
  로컬 세션 상태 이슈였음.
- 취소 탭에서 실제 취소된 2건 조회, 상세 패널에서 제출→승인·1차→취소 이력과 스테퍼 상태
  정상 렌더링 확인. 전결 승인 등 기존 상태(대기/승인/반려)도 회귀 없음을 확인.

## 남은 범위

- `CANCELED_AFTER_APPROVAL`(승인 확정 후 취소)은 `leave.service.ts`상 아직 미구현("범위 밖")
  — 이번 작업은 필터·카운트·표시 로직에 해당 상태를 포함해뒀을 뿐, 실제로 이 상태가
  발생하는 흐름은 후속 작업 대상이다.
