## 현재 변경 사항

!`git status --short`

!`git diff --staged`

## 최근 커밋 스타일 참고

!`git log --oneline -10`

## 지시사항

위 diff를 분석해 아래 컨벤션에 맞는 커밋 메시지를 작성한 뒤 커밋한다.
스테이징된 변경이 없으면 커밋하지 말고 `git status` 요약과 함께
"스테이징된 변경이 없습니다"라고 알린다.

`git status --short`에 새로 추가되거나(`??`, `A`) 삭제된(` D`) 파일이 있다면,
커밋 메시지를 작성하기 전에 `git add`(신규/수정) 또는 `git add -A`(삭제 포함)로
먼저 스테이징한 뒤 진행한다.

### 형식 (Conventional Commits + 한국어)

```
<type>(<scope>): <제목 — 한국어, 50자 이내, 마침표 없음, 명사형 종결>

<본문 — 선택. "무엇을"이 아니라 "왜"를 쓴다. 72자 줄바꿈>

<푸터 — 선택. 관련 이슈/기획서 참조>
```

### type (아래 중 하나만)

| type | 용도 |
|---|---|
| feat | 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| perf | 성능 개선 |
| test | 테스트 추가·수정 |
| docs | 문서(기획서·README 등) |
| chore | 빌드·설정·의존성 |
| db | DDL·마이그레이션 변경 |

### scope (이 프로젝트의 모듈 — 해당 없으면 생략)

`approval`(결재), `balance`(연차·유대 잔여), `roster`(근무표), `attendance`(출퇴근),
`auth`(인증·기기), `notification`(알림), `export`(마감·내보내기), `ui`(공통 UI/UX)

### 작성 규칙

1. **하나의 커밋 = 하나의 논리적 변경.** diff에 성격이 다른 변경이 섞여 있으면
   (예: 결재 API 수정 + DDL 변경) 커밋하지 말고 분리 커밋을 제안한다.
2. 제목은 diff를 안 본 사람도 이해할 수 있게. "수정", "변경" 같은 단독 동사 금지.
3. 본문은 다음 중 하나라도 해당하면 필수:
   - 정책 결정(D-1~D-12)이나 기획서 조항과 연관된 변경 → 근거 조항 명시
   - 되돌리기 어려운 변경(DDL, 상태머신 전이 규칙, 계산식)
   - 리뷰어가 "왜?"라고 물을 만한 선택
4. 푸터에 관련 문서를 참조할 수 있다: `Refs: 개발기획서 v3.1 §3.4`
5. 이모지, 영어·한국어 혼용 제목, AI 작성 언급(Co-Authored-By 등) 금지.

### 커밋 전 안전 점검 (필수)

- diff에 API 키·비밀번호·토큰·내부 서버 주소 등 시크릿이 보이면
  **커밋하지 않고** 해당 파일·라인을 지적하며 중단한다.
- diff에 실명·연락처 등 개인정보가 보이면 동일하게 중단하고 알린다.
- `git push`는 사용자가 명시적으로 요청한 경우에만 수행한다.

### 예시

좋은 예:
```
feat(approval): 유급휴일대체 신청 유형 추가

기획서 v3.1 C-2 반영. 잔여 검증은 substitute_holiday_balance를
참조하며, 당해 연도 소멸(D-11)은 앱 레벨에서 차단한다.

Refs: 개발기획서 v3.1 §3.1, D-10~11
```

```
fix(balance): 2단계 결재 중간승인 시 reserved 이중 해제 수정
```

```
db: approval_history에 서명 스냅샷 경로 칼럼 추가 (D-12)
```

나쁜 예:
```
수정                          ← 무엇을 왜 수정했는지 알 수 없음
feat: update approval logic   ← 영어 제목, scope 없음, 모호함
버그 수정 및 기능 추가 및 리팩토링  ← 여러 변경이 한 커밋에 섞임
```
